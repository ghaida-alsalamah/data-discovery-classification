# Classification benchmark root-cause audit

The frozen scanner and labels were inspected at `431e34a`. This audit keeps the published strict scores and distinguishes errors in the model, adapter, fixture and acceptance criteria. The previous result measured a real transfer problem, but the size of the gap cannot be attributed to a single failing model.

The authors' released micro-selected checkpoint, official fold and evaluator produced that result. The paper's cross-validation aggregate is a separate figure. ## Why the local scores are low

| Finding | Measured impact and interpretation |
| --- | --- |
| DoDuo taxonomy coverage | Only 17 of 72 holdout truth fields have an exact mapping. The currently mapped classifier can score at most 23.6% exact even with perfect supported predictions. It got 4 of 17 supported fields and emitted 48 unmapped top labels. Coverage accounts for 55 of the 68 exact misses, while 13 supported misses still show a transfer problem. The development result repeats the pattern: 14 exact hits across 414 fields and 14 of 87 on covered truth. |
| Deliberately difficult samples also lack positive controls | The shared holdout generator uses the same template families across sectors. National and residency ID shaped values were 0/106 checksum-valid each. Phone shaped values were 0/70, 0/106, and 0/106 format-valid across the three sectors. The IBAN column had 0/116 format-valid values. The ID expression creates residue 8 under the existing checksum and business codes share the ID generator. The labels express intended personal use, which is a valid stress test, but this split cannot measure healthy format recognition separately from corrupt-data behavior. See [fixture generator](upstream_holdout.py) and [validators](../backend/app/classification/detectors.py). |
| Field domain labels come from table membership | All 72 fresh fields inherit the single domain on their table declaration. Two domains are outside the engine taxonomy, accounting for 24 fields. The current result rises from 29.2% strict to 58.3% when unsupported domains are scored as unknown. This difference captures 21 unsupported fields correctly left unknown. Among the 48 fields with supported domain truth, only 21 were correct (43.8%). The benchmark cannot verify mixed field-domain agreement with an independent field-by-field annotation. |
| Per-field difficulty metadata is incomplete | All 72 fresh fields and 246 of 414 development fields lack an explicit difficulty marker. The scorer defaults them to clear. A missing or empty fresh difficult-name metric does not establish performance on ambiguous names. See [rows_for](score.py). |
| Scope and privacy tasks differ | The current engine takes schema and aggregate profiles. DoDuo sees at most 12 sampled non-null cells per column, caps tokens and groups at most 15 neighboring columns, and sees neither headers nor keys. In the holdout all tables have 12 columns, so the chunk limit did not split them. The 32-token content cap truncates 46 of 72 columns. A pinned WordPiece vocabulary check found zero unknown tokens in the 111 sampled cells containing Arabic. Text truncation and a shift in column meanings are plausible limits; wholesale token loss from Arabic characters was not observed. The scanner passes a schema that includes declared FK metadata to the current engine, but passes the separate relationship inventory to downstream analysis only. Neither the NER nor DoDuo receives either source of link evidence. The current engine missed nine linked fields and two direct identifiers on the holdout. |
| Evaluation is reproducible but intentionally strict | Input file hashes and engine fingerprints match the seal. Inference reads database and profiles without reading label files. Exact accuracy keeps unsupported types as misses. Open-set scoring separately credits abstention, while broader category scoring conflates unsupported strings with unknown unless coverage is reported. Development direct-PII truth uses a semantic-type proxy. Fresh direct truth is explicit. |

The same validity gap repeats across all three earlier fixture families. In the 414-field benchmark profiles, none of the 1,729 phone-shaped samples in labeled phone fields passed the format check. None of 2,027 ID-shaped samples in national or residency ID fields passed the checksum. None of 808 Saudi IBAN-shaped samples in labeled IBAN fields passed the format check. These are sampled counts from the frozen profilers. The independent schemas can test transfer across names and layouts, but shared invalid-value conventions limit what they establish about correctly formatted enterprise data.

## Manual case inspection

| Example | Verdict |
| --- | --- |
| `borrower_full_name` was correctly labeled a personal name by the current engine. DoDuo returned `name` at approximately 1.0. | Plausible broader equivalent. `name` alone does not establish an individual's identity, so an exact PII mapping would overclaim. |
| `nearest_town` labeled city received `location` from DoDuo and unknown from the current engine. | Broader label is defensible, exact city remains a miss. Municipality names and bilingual aliases are useful evidence. |
| `receipt_state` labeled payment status received status with the correct finance domain. | Valid semantic parent. The payment subtype requires the ledger context. Keep the original strict miss. |
| `division` labeled category was predicted department by the current engine and name by DoDuo. | Genuine errors on a supported type. The templated tier-like values provide weak evidence for a named department. |
| `z_address_map` labeled `geo_polygon` contains WKT POINT values; current engine abstained. | Unsupported truth and an apparent generator/label mismatch. A point has different geometry from a polygon. |
| `emergency_tel` was correctly detected as a phone field even though 106 of 106 phone-shaped samples fail the format check. | Correct semantic intent and a separate quality failure. A detector that requires valid values would predict differently on this fixture. |
| `visitor_pass` predicted Saudi residency ID, while `postal_tag` intended as residency ID received generic identifier. | Genuine false positive and subtype miss under intent-based truth. Both share shaped values and all shaped identity positives are checksum-invalid. Misleading names make abstention defensible, and the fixtures lack valid-value controls for attribution. |
| `account_ref` correctly marked linked via a resident reference, whereas `after_hours` was typed correctly but marked nonpersonal. | Distinct linkage outcomes. The FK supplies evidence for the first. The latter sits beside a synthetic technician name with no person key, so treating the flag as linked depends on the stated business purpose and identifiability. |
| `item_ref` is marked nonpersonal even though it sits in a borrower ledger. | Linkage policy is underspecified. The target is a public catalog item, but the stored loan association can identify a borrower's activity. The verdict depends on whether the requirement concerns standalone values or the identified record. |

## Elm Challenge 1

The supplied phase briefs describe read-only source connectivity, schema and relationship discovery, profiling, classification and sensitivity, domains, and quality/opportunities. The official Elm Challenge 1 prompt or rubric was not found in the shared project, attachments or public search. Exact field-level domain, a fixed taxonomy of fine subtypes, and forced binary judgments on corrupt or weakly linked data are local benchmark choices. Their status as official requirements is unverified. The predictions include outputs for the other capabilities, but the comparison scorer does not assert their outcomes.

| Capability from the supplied briefs | What the current comparison verifies |
| --- | --- |
| Connect to data sources | Runs SQLite successfully. The comparison provides no acceptance evidence for other connectors. |
| Inventory schema and relationships | Checks exact coverage of classified field names against labels. It does not score relationship discovery or data types. |
| Profile data and flag quality issues | Exports profiling and quality. Ground truth and metric assertions for profile statistics and quality findings are absent from this scorer. |
| Classify and identify sensitive personal data | Scores semantic labels, direct identifiers, broad personal linkage and review. It does not score sensitivity tiers directly. |
| Group data into useful domains | Scores exact field domain with the limitations above. It does not assess table-level or asset-level usefulness of the grouping. |
| Identify usable analysis opportunities | Exports opportunities and readiness. It does not grade suggested opportunities or check positive readiness cases. |

The fastest evidence-based route is to keep the frozen scanner, obtain the official brief and one representative redacted schema with a data dictionary, then create a new independently reviewed acceptance set. Record expected coverage per requirement, valid and corrupted identifier controls, verified and inconclusive person links, and domain/type resolution that the inputs support. Retain the existing strict benchmark as a stress test and publish the new acceptance scores alongside it. Before considering a model change, rerun the existing scanner and its released components on the new set. Focus any subsequent changes on verified acceptance failures.
